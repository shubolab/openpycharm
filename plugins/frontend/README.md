# Native frontend candidate — isolated, default off

This is an independent native TypeScript/JavaScript LSP provider for the pinned
open-source PC-261.26222.68 SDK. It is **not included in production packaging**,
does not replace the native editor with a web surface, and contains no
proprietary JavaScript plugin code.

The provider uses the existing `com.intellij.modules.lsp` module and
`com.intellij.platform.lsp.integrationProvider` extension. It preserves normal
`TrustedProjects` checks. It returns before service lookup for files outside a
compiled, owned `.tools/frontend-m0-fixtures/fixture-<nonce>` boundary.

## Explicit tools and server checks

Use Python 3.10 or newer, as required by the repository build helpers:

```sh
python3 scripts/provision_frontend_tools.py --target macos-arm64
python3 scripts/frontend_protocol_probe.py --receipt /absolute/printed/frontend-tools.json
python3 scripts/build_frontend_plugin.py --sdk /absolute/authenticated/PC-SDK --test --worker-fixture /absolute/generated/fixture
```

These commands provision tools, run a standalone stdio server, or compile a
plugin/helper JVM. They do not launch an IDE. The provisioning CLI is the only
network acquisition path; the compiler and protocol probe remain offline and
fail if authenticated tools are missing. Opening an editor file never downloads
tools or runs npm/install scripts.

`tools.lock.json` pins exact official Node 24.22.3 Mac arm64/Windows x64 archive
bytes, TypeScript Language Server 6.1.0, and TypeScript 6.0.3. Every archive has a
size and SHA-256; every npm artifact also has SHA-512 SRI. The published TLS CLI
bundle's authenticated source map identifies 21 embedded npm packages. Their
exact corresponding official archives and complete legal files are locked and
retained. Node's original aggregate LICENSE, TLS LICENSE (including copied MIT
code), TypeScript LICENSE/ThirdPartyNoticeText and all 21 original dependency
licenses remain in the runtime cache. Node's npm tool distribution is not used
or copied. Dependencies are extracted without invoking a package manager.

Extraction rejects traversal, duplicates and selected links/special files. The
published runtime has a pinned per-file manifest, so editing both a payload and
its cache receipt cannot authorize new bytes. Only this checkout's own `.tools`
may receive caches or build outputs; source SDK/reference/user files are never
modified.

## Native lifecycle candidate

The canonical provider now overrides the public `startServerProcess` hook with
an actual SDK `OSProcessHandler`, preserving CRLF framing. Its stdin has one
bounded FIFO owner and a two-second write deadline. Request-thread interruption
does not truncate an accepted shared document notification. Writes/authentication/
process starts reject the Swing EDT; dispose only schedules independent cleanup.
Normal project disposal registers the exact handler, and completed handlers are
removed from that disposable tree.

Cleanup does not wait for the LSP writer lock. It signals only the spawned main
process and observed descendants whose PID and start time still match; missing
main identity fails closed. Reused/unverifiable child IDs are not signalled, and
incomplete identities/over-limit trees cannot report successful cleanup. The
native hook does not install a dedicated POSIX session or Windows Job: discovery
of descendants that reparent during an unexpected parent crash remains unverified.
Do not transfer the protocol CLI's stronger owned-session/job result to this hook.

Explicit headless native-process control (starts owned Node/TLS, never an IDE):

```sh
python3 scripts/build_frontend_plugin.py --sdk /absolute/authenticated/PC-SDK --test \
  --worker-fixture /absolute/generated/fixture --process-fixture /absolute/generated/fixture
python3 scripts/frontend_native_api_audit.py --sdk /absolute/authenticated/PC-SDK \
  --build-report .tools/your-build-report.json
```

The builder's ordinary `--test` remains process-free. `--process-fixture` is the
explicit process test: it authenticates the complete existing cache, checks real
TS/JS unsaved completion and cancellation followed by a shared document change,
then on POSIX stops only its owned Node to force a real full-pipe timeout. An
external test JVM session/job watchdog owns all test descendants on failure.
These controls are not native `LspClientManager`, editor/PSI or UI acceptance.

## Deferred native gate

No native application startup is performed by this M0 implementation. A later
owned-profile test must supply all these properties explicitly, using a fixture
and tools receipt generated by the protocol CLI:

* `openpycharm.frontend.m0.enabled=true`
* `openpycharm.frontend.m0.fixture=<exact generated fixture root>`
* `openpycharm.frontend.m0.nonce=<marker nonce>`
* `openpycharm.frontend.m0.toolsReceipt=<exact frontend-tools.json>`
* `openpycharm.frontend.m0.toolsReceiptSha256=<receipt SHA-256>`

These are activation data, not an instruction to launch the application now.
The compiled worktree boundaries intentionally make this a local M0 test plugin,
not a generally redistributable project feature.

The file-open callback only performs memory checks and registers a descriptor.
Filesystem/hash authentication is guarded against the Swing EDT and runs in the
native API's worker `createCommandLine` path. The descriptor authenticates the
owned fixture marker, source-lock identity, cache receipt, full payload set and
all file hashes before returning a command. It never writes a runtime cache.
Initialization options use immutable paths, avoiding assumptions about native
callback order.

The child environment is private to language analysis, with owned HOME/temp/
cache/log paths and no inherited Git/npm/service tokens or Node injection
options. This does not modify user-selected Git/private-repository/npm/service
authentication outside the child. The language server receives an explicit
TypeScript SDK path, UTF-16 positions and disabled automatic typing acquisition.

## Evidence boundaries

The real protocol probe checks incremental UTF-16 initialization, unsaved TS/JS
completion, diagnostics, cross-file definition after an emoji, an incremental
type-error change and recovery, unchanged disk sources/tool payloads, and normal
shutdown of the owned process group. Remaining unused-symbol hints are recorded,
not suppressed. This proves server behavior, **not native editor integration**.

The plugin checks compile against the real SDK and read every JAR entry through
the actual IntelliJ archive reader. Pure Java tests cover default-off/non-fixture
boundaries; a worker helper authenticates the real cache and rejects changed
activation receipts without starting Node or an IDE.

Still open: native PC module/EP/service activation and the native client-manager stdio connection,
completion/diagnostic/navigation UI, cancellation/project disposal in the native
client, and actual Windows execution. HTML/CSS, templates, DAP/browser debugging,
production packaging and full PyCharm parity are outside this M0.

## Optional product assembly candidate

The original M0 provider remains a separate, explicitly activated experiment.
The product provider has its own `dev.openpycharm.frontend` ID and settings,
uses the normal project trust state, and includes the pinned local runtime.
It is enabled for trusted project JavaScript/TypeScript files. Building or
starting this candidate does not establish full frontend or PyCharm parity.

The ordinary assembler still produces the published four-plugin product.
To explicitly include the fifth plugin in a new `0.1.0-dev.4` assembly, first
run the provisioner, then pass its printed absolute `receipt` path:

```sh
python3 scripts/provision_frontend_tools.py --target macos-arm64
python3 scripts/package.py --target macos-arm64 --sdk /absolute/authenticated/PyCharm.app \
  --version 0.1.0-dev.4 --output build/frontend-candidate/OpenPyCharm.app \
  --frontend-runtime-receipt /absolute/repository/.tools/frontend-m0-tools/runtime/macos-arm64/LOCK_SHA/frontend-tools.json
```

Use `windows-x64` and its authenticated SDK/receipt for Windows. Provisioning is
an explicit network step; the builder and assembler never download or run Node.
The complete runtime, original notices, relative manifest and executable modes
are copied under `third-party-plugins/openpycharm-frontend/runtime/<target>`.
The assembler, startup probe and installer authenticate all of those files;
frontend cannot fall back to validating only its JAR. The Java compiler output
proof is checked separately from the outer JAR checksum.

The installer workflow has an optional `frontend` dispatch input, default off.
For this candidate, select version `0.1.0-dev.4`. The extra CI gate checks the
actual SDK JVM worker/settings controls and authenticates the full bundled
runtime without starting Node. The existing native startup gate requires the
fifth plugin to be loaded with its exact version. Actual native LSP editor,
project-close and Windows lifetime acceptance remain separate evidence.
No new installers or release are implied by these source-level integration
changes. A publishable release also needs a new real installed-version README
GIF and capture manifest.
